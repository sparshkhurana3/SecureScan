## Deviations from the plan or the task text (with reason)

1. **Backups are per-part encrypted files in a directory, not one archive.** Each part (`db-*.dump.age`, `artifacts.tar.age`, ...) is streamed through `age`; no plaintext ever touches the disk, no second copy of hundreds of GB is needed, and a damaged part is isolated. `MANIFEST.txt` and `SHA256SUMS` are the only unencrypted files. Restore verifies the checksums and test-decrypts every part first.
2. **No WAL archiving**, only a nightly `pg_dump --format=custom` of the three databases: the design mentions "continuous WAL archiving" but the plan task (M11 task 4) and the 24 hour recovery point are met by the nightly dump. WAL archiving can be added later without changing the scripts.
3. **The secrets are in the backup by default** (`secrets.tar.age`, without the age key), so that a restore on a fresh machine is complete; `BACKUP_INCLUDE_SECRETS=false` turns it off. Recorded as a residual risk in `docs/security-checklist.md`; the age private key must live in a vault, not only on the machine.
4. **A backup counts as a success only when copied off the machine and verified there** (`sha256sum -c` on the remote); `--no-offsite` never updates the success metric.
5. **The "last successful backup" metric travels through a file in the data volume** (`backup/status.json`, written by `backup.sh` via `docker exec` into the worker) read by a worker start-up task, plus an optional node_exporter text file. The host script cannot reach the worker's registry otherwise.
6. **Host check: refuse to start the worker, not the scans one by one.** The plan says "refuses to start scans"; I did it as `HostCheckError` in a worker start-up hook (the worker stops with the reason in its log) because `scan_job.py` and the executor are not mine. `SECURESCAN_HOST_CHECK=warn` (the default in dev and test) only logs. Docker's version comes from the `Server` and `Api-Version` headers of `/_ping` (the proxy forbids `/info` and `/version`); Docker below API 1.44 blocks, Engine below 29 only warns.
7. **Regression gate through the normal scan path** (as the task asked) is the shared implementation; M8's gate for *candidate Semgrep rules and Nuclei templates* in `jobs/updaters.py` keeps running the candidate in its own updater container because the Semgrep builder always mounts the *active* rules (see "Open issues"). Both read the same expectation files.
8. **Image proposals cover every lock image, in two scopes.** `runtime` (scanners, SonarQube server, squid, skopeo, ZAP, Nuclei) takes effect at the next scan after approval; `release` (PostgreSQL, Python, Node, nginx, socket proxy, DefectDojo, Valkey) is a notice (`regression_result = skipped`, approving refused with `image.release_scope`): those images are part of the Compose bundle and change with the next release, not at run time. Major versions of PostgreSQL, Python, Node and DefectDojo are never proposed (`KEEP_COMPONENTS`).
9. **Only images whose digest the job records can be gated** (Semgrep, Gitleaks, Grype, Dependency-Check, SpotBugs, the SonarQube scanner). The gate checks that the scan's jobs ran the candidate digest and reports `error` otherwise (fail safe, never a false pass). Syft (inside the syft-grype job), the SonarQube server (created by the lifecycle task), squid, skopeo, ZAP and Nuclei are stored as `skipped`: approval needs `acknowledge_skipped`, meaning the Admin tested by hand. An unasserted suite (all expectations still `verified: false`, which is the case until the first real run) is also stored as `skipped`.
10. **Image overlay rows carry the lock name** (`regression_detail.lock_name`) and the catalogue overlay matches by lock as well as by tool, because Grype's scan, database-update and status entries share one image: approving the Grype image must change all three. The row is stored under the entry that scans (`syft-grype`).
11. **A candidate runs only with a one-time token**: the row in state `testing` holds `regression_detail.candidate_token`; the regression scans carry it in their job options (`tool_options.<job tool>.image_candidates`); the overlay accepts nothing else. The token is stripped from API output. This stops an ordinary scan request from running an unapproved image.
12. **Container hardening exceptions** (documented in the compose file and the checklist): `db` keeps a writable rootfs and five capabilities; DefectDojo's services are defined by the vendored upstream file and `override.yaml`, which Compose does not allow `compose.yaml` to modify; the ready-to-paste hardening is below. `/tmp` is not `noexec` (git's credential helper runs from there, M3). The socket proxy runs as root unless `SOCKET_PROXY_USER` is set, because a wrong group id would break all scanning.
13. **No Grype scan of SecureScan's own images, no Playwright run, no tick of the checklist, no `v1.0.0` tag** (plan M11 tasks 8 and 10): they need running services and the user. The checklist gives the commands; nothing in it is ticked.
14. **The Settings page for scanner images is not written** (frontend is not mine). `docs/runbooks/approving-image-digest.md` has a browser-console fallback.
15. **Performance indexes are not added.** Task 9 says "add indexes if not" met; the numbers do not exist yet. `docs/runbooks/performance.md` lists the candidate indexes and how to decide with `EXPLAIN` on the seeded database; no migration was created to avoid colliding with other milestones' revision numbers.

## Things the next person should know

- The SonarQube December rule is encoded twice on purpose: in the proposal selection (`select_candidate`) and again at approval (`check_approvable`, code `image.december_rule`); the unit tests cover same-year, December, year-skip, downgrade and non-community tags.
- Overlay precedence is: regression candidate (token-bound) > approved `ImageVersion` > `SECURESCAN_IMAGE_<LOCK>` environment > catalogue digest > lock file > tag (dev only). It is tested with fake sessions (the SQL itself, including the lock match, only runs against PostgreSQL).
- The worker's lock-file mount is a single-file bind mount: an editor that replaces the file (new inode) leaves the container looking at the old one. `pin-images` rewrites in place; after any other edit run `sc up -d --force-recreate api worker`.
- `scripts/restore.sh` refuses to run onto a project that has containers or a PostgreSQL cluster. A drill therefore needs a clean machine (or `python3 scripts/dev.py down --volumes` first), which is the point.
- Regression runs create the applications `regression-<app>` (tag `regression`) with real scans, reports and DefectDojo products. They are history like any other and are never deleted.
