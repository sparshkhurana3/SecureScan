# M6 part 2 build notes: SAST scan, DAST scan, scan detail, report view

Written on a machine with no Docker, uv, Python 3.14, Node 24 or installed dependencies, so **nothing was executed**: no `tsc`, no
`eslint`, no `vitest`, no Playwright. Every file was desk-checked against the backend routers and the page shell / UI kit of the
other frontend agent (F1). The only command that ran is `python scripts/check_imports.py` (Python only, 0 problems; it does not look
at the frontend). Expect a short round of type and lint fixes on the first `npm run typecheck && npm run lint && npm test` on Ubuntu.

## Deviations from the plan, and why

1. **Credentials are per target.** The plan says "GitHub URL + credential picker". The API has no free-standing credential: a deploy key or
   vendor token is created for an existing `vendor_repo` target (`POST /credentials/deploy-key|vendor-token` with `target_id`). The form therefore
   creates application, version and target first, then the credential; "use the stored one" means the target's current `credential_id`.
   A vendor application's repository address becomes a `vendor_repo` target, an internal one a `github_repo` target (read through the GitHub App).
2. **Chunks go through the `formData` slot of `apiFetch`.** `apiFetch` always JSON-encodes `body`, and the chunk endpoint wants raw bytes. The
   transport (`src/api/uploads.ts`, `asRawBody`) passes the Blob as `init.formData`, which `apiFetch` hands to `fetch` untouched, with
   `Content-Range` in `headers`. This works with the current `client.ts` but is a hack. **Request for F1 / the owner of `client.ts`:** add a
   `rawBody?: Blob | ArrayBuffer | Uint8Array` option that is sent as is and leaves `Content-Type` to the caller; then change one line in `uploads.ts`.
3. **No picker for DAST login profiles.** There is no endpoint that creates or lists `dast_login` credentials (`GET /credentials` accepts only
   deploy keys and vendor tokens), so the login profile is a text field for the profile id, enabled only when the tag is UAT, validated as a UUID.
   The field is cleared (sent as null) when the tag is production.
4. **Image tar targets** are created as `kind: "image"` with `locator: "upload:<artifact id>"` and `upload_artifact_id` set (the zip convention).
   Nothing in the backend reads that yet (M8 image intake must: a locator that starts with `upload:` means "load the tarball of
   `upload_artifact_id`").
5. **DAST profile names.** M9 had not shipped the DAST profiles when this was written. The page finds the profile of a mode by the profile's
   `mode` field, then by the name `dast-<mode>` (`dast-baseline`, `dast-full`, `dast-api`, `dast-nuclei`). A mode without a profile is shown disabled
   with "Its scan profile is not installed yet"; with no DAST profiles at all the Start button stays disabled. If M9 names the standalone Nuclei
   profile differently, set its `mode: nuclei` in the profile YAML or adjust `profileForMode`.
6. **Environment tag editing** is done in the edit form (not inline in the table), so that a slip of the mouse does not widen what may be scanned.
   The change is audited by the backend.
7. **The reports of F1's `api/reports.ts` are reused** (`useReport`, `useReports`, `useCreateReport`, `useReviewReport`, URL helpers). `api/scans.ts` only adds
   `useRecentReports` (newest ready report per scan, for the scan tables), `useReportFindings` (the open findings of the snapshot, for the conditions
   dropdown) and the review form rules.
8. **Application names in scan lists** come from the application list and the version labels from `GET /versions/{id}` (cached 5 minutes); `ScanOut` has ids only.
   A list of 25 scans costs at most 25 small requests the first time.
9. Version label kind chosen automatically: `branch` for repositories, `upload` for zips, `image_digest` or `tag` for images, `release` for DAST targets.
   Editing the version label of an existing target is not offered.
10. The vendor authorization of a SaaS target is entered on the target form (document upload, window, contact, notes) and checked there; the scan form
    shows its status and says the scan is refused without it. The refusal itself (and every other rule) stays the backend's.

## Not verified, and how to verify on Ubuntu 24

From `frontend/`: `npm ci && npm run typecheck && npm run lint && npm test`, then with the `dev` stack up `npm run e2e -- sast dast report`.

Likeliest first failures:
- **Typecheck / lint**: generic inference in `useQueries` (`useVersionMap`), the `as unknown as typeof apiFetch` casts in tests, `useRouter({ warn: false })` typing in
  `FormBits.tsx`, `restrict-template-expressions` or `no-unnecessary-condition`-style complaints (a few `?.` on values typed non-null), `react-hooks/exhaustive-deps` on
  the effects in `UploadWidget.tsx` and `sse.ts` (`--max-warnings 0`).
- **Vitest**: `getByLabelText` ambiguities (a label that is a substring of another is matched exactly in the tests, but check `Vendor`, `Verdict`, `Application`),
  `user.upload` with the `accept` attribute, `user.selectOptions` on the `size=N` repository listbox, Radix Checkbox inside a form (needs the `ResizeObserver` stub that
  `test-setup.ts` has), `DOMException` abort message in the upload test.
- **Playwright**: the mock OIDC form selectors (F1's helper), the first scan needs the worker and the scanner images (the SAST spec waits up to 8 minutes for the report
  link), the DAST spec's last test skips itself when the `dast-full` profile is missing, `report.spec.ts` skips itself when no ready report exists (run `sast.spec.ts` first),
  axe may flag contrast or `aria-describedby` references on pages I could not render.
- **Behaviour to look at by eye**: SSE through the dev proxy (the Vite proxy streams by default; behind nginx `X-Accel-Buffering: no` is already sent by the API), the
  sandboxed iframe (the report must render with `sandbox=""` and the CSP `style-src 'unsafe-inline'; img-src data:`), upload of a >100 MB zip with a connection drop in the
  middle (turn the network off in the browser's dev tools; the widget should retry, then offer "Try again", and resume), PDF download from the report page.

## Open issues for other milestones and owners

- **F1 / `client.ts`**: raw body option for chunk uploads (deviation 2).
- **F1 / router**: assumed and matched: `/scans/$scanId`, `/reports/$reportId`, `/sast`, `/dast`. Pages link with plain anchors that navigate through the router history
  (`AppLink`), so renaming a route does not break typechecking, only the links.
- **M8**: image tar intake for `locator: upload:<id>` (deviation 4); SpotBugs applicability by source (the tools checklist ticks every tool of the profile).
- **M9**: DAST profile names and `mode` field (deviation 5); a login profile API (create, list, delete `dast_login` credentials) so the DAST form can offer a picker;
  `Target.dast_cron` is not read by the schedule task (M7 note), the form only stores it.
- **M10**: the vendor flow reuses the vendor fields of both forms; vendor SaaS authorization is enforced by the backend scan check (`register_scan_check`), the UI only reflects it.
- **Backend nits seen while reading** (no change made): `ScanOut` has no application name or version label (extra requests above); `GET /targets` has no application name either;
  `ScanCreate.options` is free-form and the forms send none; `GET /scans` has an `active` filter that the tables do not need yet.
- If the deploy key panel is open and any field of the form is edited, the panel closes and the next Start generates a new key (the old one is replaced); say so in the
  user guide.
