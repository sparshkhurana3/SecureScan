## Interface for M3 (needs a decision by the M3 owner)

`from securescan.integrations.github.connection import clone_grant, CloneGrant`

```python
async with clone_grant(session, target.locator) as grant:   # locator is "owner/name"
    # grant.token: one-hour installation token, one repository, contents: read (never log it)
    # grant.proxy_url: run git with HTTPS_PROXY=<it> when not None
    # grant.git_host: "github.com" (or the Enterprise host)
    ... clone with CloneAuth(kind="token", secret=grant.token) ...
```

The grant also holds an egress lease, so the proxy is not idle-stopped during the clone. The brief's assumed `clone_repository(url, dest, auth, commit)` was
not used: M3 wrote `runner/sources/github.py` with `CloneAuth`/`SourceRequest` instead, and M7 never calls it. For vendor repositories (deploy key, vendor token) M3
should read the credential from `Target.credential_id` (kind `deploy_key` or `vendor_token`), decrypt with `domain.credentials.reveal_secret`, and for
HTTPS vendor repos wrap the clone in `runner.egress.egress_lease({git_host})`. `deploy_key` public key text is in `Credential.public_material`.

`create_scan` is called as `create_scan(session, version_id=, profile_name="code-standard", trigger=ScanTrigger.CHANGE|WEEKLY|SCHEDULE, requested_by=None,
target_ids=[target.id], options={"commit": sha, "trigger_detail": ..., "schedule_id": ...}, idempotency_key="system:...")`, matching the real signature in
`domain/scans.py`. M7 relies on `create_scan` queueing the jobs after the session commits (`schedule_enqueue`), and on a repeated identical queued scan collapsing.

## Behaviour worth knowing

- **Test and sync run in the worker.** Only the worker may start the egress container, so `POST /integrations/github/test` writes a "running" marker
  on the connection row, defers task `github_test` and polls the row for up to `wait` seconds (default 45). Result in `last_test_*`: ok message is exactly
  `Token minted, N repositories, ls-remote ok`; failures are plain sentences, one per line. If the answer takes longer the endpoint returns `202` with status `running`
  and `GET /integrations/github` shows the result later. `POST .../sync` defers `github_sync` and returns `202`.
- **Proxy changes recreate the container** (the socket proxy forbids `exec`, so no `squid -k reconfigure`). The allowlist of a running proxy only grows
  (union of requested hosts) until it is stopped by the idle task; every change is serialised by one `asyncio.Lock`, and a changed allowlist drops
  connections in flight (rare: only when a new host appears). Idle detection uses an in-process lease counter plus `<data_root>/egress/last_used`
  (written at most every 30 s); this assumes **one worker process**.
- **Squid runs as uid 13 (`proxy`) with a read-only root filesystem**, config bind-mounted from `<data_root>/egress/squid-<hash>.conf`, logs on a 16 MB tmpfs
  (`access_log none`; `cache_log` only). Only ports 80/443 and CONNECT to 443 are allowed, only to the listed hosts. The worker logs every start with its host list.
- **The poller** reads heads with one installation-wide read token (minted once per run, refreshed 5 minutes before expiry), not one narrowed token per repository,
  to stay inside the request budget. Clone tokens are narrowed (`clone_grant`). `last_scanned_sha` is set when the scan is enqueued; a head change while a SAST scan of
  the application is queued or running only updates `last_seen_sha` and is picked up on the next run after the scan ends. A failed scan is not retried until the
  next push or the weekly scan. Per run at most `github_poll_max_scans_per_run` (25) scans are enqueued, the rest follow on later runs. A weekly scan does not update
  `last_scanned_sha`, so a repository may get one extra change scan after its weekly scan.
- **Schedules**: `next_run_at` is stored; missed runs collapse into one; a run due inside a blackout window waits (at most 24 h, then that occurrence is skipped). A
  `poll` schedule row only switches the poller off or raises its minimum interval (the periodic cron stays `github_poll_interval_minutes`). DAST schedules call
  `create_scan` and report rejections (for example the production rule) in `last_status`.
- **Credentials**: a deploy key or vendor token replaces the target's `credential_id`; the old one is revoked only with `replace=true` (otherwise 409). A vendor token
  needs an expiry date. Private keys, tokens and passphrases are never in responses, audit details or logs (key fingerprints only).
- **Private keys of the App** can be uploaded in Settings (two slots, encrypted as `github_app_key` credentials) or supplied as Docker secrets via
  `SECURESCAN_GITHUB_APP_KEY_1_FILE` / `_2_FILE`; an uploaded key wins for its slot.

## Deviations

1. Cron evaluator written in-house instead of adding `croniter` (testable without installs; five fields, names, steps, dom/dow OR rule).
2. Test and sync are asynchronous through the worker (the plan describes them as plain API calls); required by "only the worker talks to Docker".
3. Extra endpoints: `GET /credentials`, `DELETE /credentials/{id}`, `DELETE /schedules/{id}`; extra tasks `github_sync`, `github_test`, `schedule_evaluator`.
4. Extra hook module `credential_alerts.py` adds `expired` and `unused_warning` notices; the 14-day notice is M2's.

## Not verified, and how to verify on Ubuntu 24

Run from `backend/`: `uv run ruff format . && uv run ruff check . --fix && uv run mypy securescan && uv run pytest tests/unit -k "github or egress"`.

- **Ruff E501**: several docstrings, strings and comments are longer than 100 columns (`ruff format` cannot wrap them); expect to wrap a few dozen lines.
- **Unit tests were never run** except the scheduling file. Likeliest first failures: `httpx.AsyncClient(proxy=...)` keyword (httpx 0.28), async handler for `httpx.MockTransport`
  in `test_requests_are_serial`, pydantic validation of `UUID` strings in `test_vendor_token_*`, `Settings(...)` keyword construction in `test_egress.py`, and the
  `monkeypatch.setitem(sys.modules, "securescan.domain.scans", ...)` trick in the poller store tests.
- **Squid** (`runner/egress.py`): run a test from Settings and `docker ps` must show `securescan-egress` on networks `securescan_backend` and `securescan_egress`; it must disappear
  after 5 idle minutes. Unknown until run: the image's `/usr/sbin/squid` path, whether uid 13 can start squid with `-N` and a tmpfs `/var/log/squid` (`uid=13,gid=13` mount options),
  and `pid_filename none`. `docker logs securescan-egress` shows startup errors only if squid writes to stderr; if it exits at once try running the image by hand with the same flags.
- **Socket proxy policy (M3)** must allow: `GET /containers/{name}/json`, `POST /containers/create` with `name` and several networks, start, stop, `DELETE /containers/{id}?force=1`, and bind mounts
  of `<data volume>/egress/*.conf`.
- **Compose** (not owned by M7): pass `SECURESCAN_EGRESS_IMAGE: ${IMG_SQUID}` (digest form) to `worker`; optionally `SECURESCAN_GITHUB_APP_KEY_1_FILE: /run/secrets/github_app_key_1`
  with the matching secret. `deploy/images.lock.yaml` still has SQUID tag `latest` (must be pinned by `pin-images`; the code refuses an unpinned image outside dev).
  In dev set `SECURESCAN_EGRESS_ENABLED=false` to connect directly.
- **Network path of the worker**: `backend` is a routable network in `compose.yaml`, so the worker could reach the internet without the proxy; the proxy is policy, not a hard barrier. Decide in M11.
- **SSH deploy-key clones** use port 22, which squid does not carry (only 80/443). M3 either allows direct SSH egress for the worker or uses `ssh.github.com:443` through a `ProxyCommand`.
- **GitHub details to confirm with the S6 test App**: `POST /app/installations/{id}/access_tokens` accepting `repository_ids` with `permissions`, the `X-GitHub-Api-Version: 2026-03-10` value,
  `GET /installation/repositories` working with an installation-wide `contents: read` token, `GET /app/installations/{id}` returning `permissions` and `account.login`, and
  `git ls-remote` with the askpass script (`x-access-token` as user name).
- **Acceptance walk-through** (plan M7): Settings test message; push to a confirmed automatic repository starts one scan within 10 minutes and a second push during the scan queues nothing;
  weekly schedule via `POST /schedules {"name":"Weekly","kind":"weekly"}` (default Sunday 02:00 UTC, automatic set); deploy key via `POST /credentials/deploy-key`;
  `grep -r ghs_ /var/lib/securescan` finds nothing (tokens are only in memory, in the git process environment and in M3's 0600 credential file during a clone).
