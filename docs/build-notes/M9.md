# M9 build notes: DAST (ZAP and Nuclei)

Written on a machine with no Docker, uv, Python 3.14, Node or installed dependencies (pydantic, FastAPI, SQLAlchemy and pytest are not even
importable), so **the milestone was never run as written**. What was possible: `python scripts/check_imports.py` (byte-compile on Python 3.9
and the name cross-check, 0 problems in the files below), `yaml.safe_load` of every YAML file, reading each test against the code it tests, and a
throw-away harness (not committed) that loaded `dast_rules.py`, `dast_egress.py`, `zap.py` and `nuclei.py` against a tiny fake pydantic and stubbed
third-party imports and ran the pure parts of `test_dast_rules.py` (159 cases, every rule table), `test_dast_plans.py` (the rendering tests, 25),
`test_dast_egress.py` (31) and the Nuclei helpers. The harness found one real bug (Python rejects Java's `\Q...\E` regex quoting; fixed with
`check_java_regex`). The remaining failures there were harness limits only (no nested models, no Literal checks, no catalogue). Everything that needs
`DefaultToolBuilder`, the catalogue models, FastAPI or SQLAlchemy (the builder tests, the API tests, the integration test) was reviewed by reading only.
The tests were written for Ubuntu and have not been run under pytest.

## How it fits together

- **Creation.** `create_scan_result` calls `check_scan_allowed_async` for dast profiles right after choosing the tools, so the API answers a production
  violation with a **403** problem (`dast.production_baseline_only`, `dast.production_no_login`) in plain words. The older generic check in
  `domain/scans.py` (422) stays behind it as a backstop and still has its own tests. Other 403 codes: `dast.vendor_authorization_required`,
  `..._not_started`, `..._expired`, `dast.host_not_allowlisted`, `dast.host_unresolvable`, `dast.host_blocked`, `dast.blackout_window`,
  `dast.blackout_invalid`. 422 codes: `target.environment_required`, `dast.api_spec_required`, `dast.mode_tool_mismatch`. 503:
  `dast.lock_not_configured` (a DAST tool whose catalogue entry lacks `lock: dast`).
- **Running.** The `url` source handler gives the job an empty workspace. `prepare` of a builder asks the rules again (a queued scan can outlive
  a vendor window or run into a blackout), starts the job's squid (`dast` + `egress`, config allows only the target host and API definition host on
  their ports), renders the plan to `config/plan.yaml`, and builds the scanner on `dast` only with the proxy switches. The squid is removed by
  `post_run` on the normal path and by the watcher on every other path (failed, cancelled, timed out, queued again, worker crash after the next DAST
  job starts). The Stop button is the existing `POST /scans/{id}/cancel`.
- **Secrets.** A login profile is a `dast_login` credential: settings in `Credential.extra` (not secret), user name, password, TOTP seed or header value
  as JSON in the encrypted `ciphertext`. The plan refers to `${ZAP_AUTH_USERNAME}`, `${ZAP_AUTH_PASSWORD}`, `${ZAP_AUTH_TOTP_SECRET}`,
  `${ZAP_AUTH_HEADER}`, `${ZAP_AUTH_HEADER_VALUE}`; the values are container environment of the ZAP container only. Tests assert that the secret is in
  neither the argv, the plan text nor the stored `zap-plan.yaml`. Any `${` inside user-supplied login settings is refused.
- **Stored with the job**: `zap-plan.yaml` (the exact plan), `dast-proxy-access.log` (squid's access log), a coverage note "Scan proxy: N requests to
  <hosts>; M refused" (with a WARNING if a host outside the allowlist was served), the scope as applied exclusions, `content_versions.nuclei_templates`.

## Deviations from the plan or the task text (also to be recorded in docs/decisions.md)

1. **Plan file location.** `plan.yaml` is in the read-only `config` mount (`/zap/config`), not in `/zap/wrk`: `/zap/wrk` is the writable output mount and
   a plan there could be overwritten by the scanner. The plan is also stored as an artifact.
2. **ZAP exit 1 with a login profile is `failed`**, not `completed_partial`. A plan error may be the failed login check, and importing a crawl of the
   logged-out application would be a false clean report (design: "the job fails if the logged-in indicator disappears"). Without a login 1 stays partial.
3. **Login check.** For form, JSON and browser logins the first job is a `requestor` job as the scan user with a `stats` test on ZAP's authentication
   statistics (`scanners/dast/templates/auth-verify.yaml`), so a broken login ends the plan before anything is attacked. The header method has no ZAP user:
   a `replacer` job adds the header (only to the target origin) and a `requestor` job requires `expected_status` from `poll_url`.
4. **Proxy lifecycle without an executor hook.** The executor has no cleanup hook for a builder, so the proxy is removed by a background watcher plus
   `post_run`. If you add `cleanup = getattr(self.builder, "cleanup", None)` to `JobRun._cleanup` (both builders implement `async cleanup(ctx)`), the
   watcher becomes a safety net only. Not done here: `executor.py` is not in this task's file list.
5. **Allowlist CIDRs are an environment setting** (`SECURESCAN_DAST_ALLOWED_CIDRS`, comma list), not a database setting with a Settings page: there is no
   settings table in the data model. "Explicitly approved host" is `Target.host_approved` (Admin only, M2). Fail closed: with no CIDR configured only approved
   hosts can be scanned. Loopback, link-local (cloud metadata), multicast and unspecified addresses are never allowed, approved or not.
6. **One DAST job at a time is a queue lock, not a refusal.** `lock: dast` on both catalogue entries (`job_lock_name` already honours it). The rules
   function only verifies the lock is configured (503 otherwise).
7. **Nuclei flags.** `-rl`, `-c` and `-proxy` are appended by the builder through `optional_args` (they depend on the target and the job), and `-nc` (no colour)
   was added to the fixed flags. `NUCLEI_CONFIG_DIR` is `/tmp/nuclei-config` (tmpfs), not `/content/nuclei-config`: only `out` may be writable.
   `-c` never exceeds the rate. A clean run may export no JSON file, so `classify_exit` writes `[]` when exit 0 left no (or an empty) `nuclei.json`.
8. **API mode needs a definition** (`dast.api_spec_required`, 422); a baseline profile with Nuclei, a Nuclei profile with ZAP and non-web tools in a web
   profile are refused (`dast.mode_tool_mismatch`). Baseline is allowed on UAT, also with a login profile.
9. **DAST ignores `egress_enabled=false`** (the dev switch for the shared worker proxy): the scanner is on an internal network and cannot work without its proxy.
10. **Extra endpoints** beyond the plan: target check, options, Start wrapper and login profile CRUD (there was no way to create a `dast_login` credential).
11. **ZAP report files**: XML `zap.xml` (`traditional-xml-plus`, scan type `ZAP Scan`) and HTML `zap-report.html` (optional, stored as a raw report).

## Not verified, and how to verify on Ubuntu 24

Run first, from `backend/`: `uv run ruff format . && uv run ruff check . --fix && uv run mypy securescan && uv run pytest tests/unit -k dast`.
Expect mypy findings on `Any` (launcher is untyped) and E501 on long lines. Likely first failures: pydantic validator signatures in `LoginSettings`
(`_urls` takes `info`), `LoginSecret.__repr__` override, `FakeSession.scalars` in `test_dast_api.py`, and `Settings(egress_image=...)` in tests.

Then on the real stack (`python scripts/dev.py up`, images pulled and pinned: `IMG_ZAP`, `IMG_NUCLEI`, `IMG_SQUID`):
- **ZAP, the pinned image** (the first integration run decides; all of these live in YAML or one constant):
  - `zap.sh` is on `PATH` and works with `entrypoint: [""]`; the `-config network.connection.httpProxy.{enabled,host,port}` keys (plan: "verify");
    `-silent` really suppresses update checks; whether `JAVA_OPTS=-Xmx2g` is honoured by `zap.sh` (otherwise the 4 GB cgroup limit is the only bound);
    whether ZAP runs with a read-only root file system and tmpfs on `/home/zap` and `/tmp` (if it writes elsewhere, `docker diff` shows where; the base
    builder fixes `read_only_rootfs=True`, a ZAP-specific override in `ZapBuilder.container_spec` is the smallest change).
  - Automation Framework keys: `passiveScan-config`, `spider` (`requestWaitTime`, `threadCount`, `postForm`, `processForm`), `spiderAjax`
    (`browserId: firefox-headless`, `numberOfBrowsers`; the plan also allows the newer client spider), `activeScan` (`threadPerHost`, `delayInMs`,
    `maxScanDurationInMins`, `maxRuleDurationInMins`), `openapi`/`graphql`/`soap` parameter names, `report` (`reportFile` without extension giving
    `zap.xml` and `zap-report.html`), `replacer` (`matchType: req_header` adds an absent header), `requestor` (`responseCode`, `tests`), `${ENV}`
    substitution in every string of the plan, the context `authentication`/`users`/`sessionManagement` shapes (form, json, browser, `autodetect`).
    Run `docker run --rm ... zap.sh -cmd -autorun /zap/config/plan.yaml` on a rendered `zap-plan.yaml` (from a job or from `dump_plan`) to see the parser's complaints.
  - The authentication statistic `stats.auth.success` in `scanners/dast/templates/auth-verify.yaml` (a wrong name makes every login scan fail closed).
    Acceptance: a UAT target with a form login shows the authentication statistics in the job log and fails when the logged-in regex never matches.
  - `/dev/shm` 1 GB for the AJAX spider and browser logins (set as `shm_size` in `container_spec`).
- **Nuclei**: `-dut`, `-nc`, `-ud <dir>` with a read-only templates directory, `-etags`, `-rd`, `-json-export` (does it write a file with zero results? the
  builder covers it either way), `-r` resolvers (`127.0.0.11` is Docker's embedded DNS; if Nuclei fails to resolve the target on the internal network,
  the name is resolved by squid only; try an IP-based target or give Nuclei a resolver the `dast` network can reach), that Nuclei uses the proxy for HTTPS
  (CONNECT) and makes no connection except to the target (check `dast-proxy-access.log`; plan acceptance).
- **squid** (same image as the M7 shared proxy): the directives `umask 022`, `buffered_logs off`, `access_log stdio:/var/log/squid/access.log` with a
  bind-mounted, world-writable log directory and uid 13; that the worker can read the log afterwards; `acl dast_names dstdomain` before `dst` (DNS only for
  allowed names). Readiness is "still running after 2 s" because the worker is not on the `dast` network and cannot probe port 3128.
- **Socket proxy**: names `securescan-dast-proxy-<uuid>` match the existing allowlist; `GET /containers/json?...label=` is used by the sweep. Re-run S2's
  deny test (`sh spikes/s2/run.sh enforce`): no network create or other new verb was added by this milestone.
- **Plan acceptance** (docs/implementation-plan.md M9): production accepts only `dast-baseline` (403 for `dast-full`, `dast-api`, a login profile);
  baseline against Juice Shop completes, imports as `ZAP Scan`, no POST in `dast-proxy-access.log`; full + Nuclei on UAT complete and import both reports,
  the access log shows only the Juice Shop host, a second queued DAST scan waits; from a container on `securescan_dast` `curl https://example.com` fails
  (integration test `test_nothing_leaves_the_dast_network` with `SECURESCAN_TEST_CURL_IMAGE`). Run
  `SECURESCAN_INTEGRATION=1 SECURESCAN_TEST_JUICE_SHOP_IMAGE=<pinned image> python scripts/dev.py test integration -k test_dast`.
- Juice Shop is registered with `host_approved` because the worker and the API cannot resolve a container that is only on the `dast` network.
- DefectDojo: confirm the `ZAP Scan` parser accepts the `traditional-xml-plus` report (S1 fixture), and that `Nuclei Scan` reads `[]`.
