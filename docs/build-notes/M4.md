## How the pieces behave (decisions inside the plan)

- **Import flow.** `enqueue_import` writes/reuses the outbox row, sets the job `import_state=pending`, **commits**, then defers `import_job` with
  `lock="dd-import:<version>:<tool>"` (imports into one Test run one at a time) and `queueing_lock="import:<outbox id>"`. `process_outbox` claims the row
  (`FOR UPDATE SKIP LOCKED`, `pending` to `processing`), uploads, records `dd_test_id` and the response statistics, reads **all** findings of the Test
  (`limit=200`, inactive included), appends history, stores the open counts on the job, marks it `imported`, evaluates the scan and defers
  `securescan.jobs.report_job.build_report(scan_id=...)` by name (queue `reports`, `queueing_lock="report:<scan>"`) only when the verdict just left `pending`
  (the scan row is locked, so two jobs finishing together cannot both trigger it). If `deduplication_complete` is false the row goes back to `pending` with
  `payload={"phase": "reread", "test_id": ..., "since": ...}` and `next_attempt_at` +2 minutes; the re-read skips the upload.
- **Failures** (`decide_retry`): next attempt after 1, 5, 15, 60 minutes, then every 6 hours; dead letter when the row is older than 7 days
  (`defectdojo_import_max_age_days`), or after 3 attempts when DefectDojo rejected the request itself (400, 413, 422; 401, 403, 404 are retried because an
  Admin can fix them). A dead letter sets the job `import_state=failed` and the scan stays `pending`; `POST .../replay` resets attempts and the 7-day clock.
  `import_sweep` (every minute) defers rows that are due and releases rows stuck in `processing` for 30 minutes, so no handover is lost.
- **What history holds per job:** every finding of the Test that is not mitigated (open, false positive, accepted, out of scope, duplicate) plus those
  this import closed (`last_status_update >= import start - 1 min`, else the `mitigated` day). Findings closed by earlier imports are not copied again.
  Counts on the job are open findings of the whole Test (active, not duplicate, not false positive, not out of scope, not risk accepted).
- **Nightly refresh** updates `state_now`, `flags_now`, `state_now_updated_at` for every distinct `dd_finding_id` (200 per DefectDojo request, ordered by
  id, one short transaction per batch); a finding DefectDojo no longer has becomes `state_now = "deleted"`. Then `Application.cached_counts` is recomputed.
- **Application roll-up** (`Application.cached_counts`, `last_scan_*`, `last_verdict`): open findings of the version of the application's latest finished
  scan, using the latest imported job of each tool, by current `state_now`. Written when a scan's verdict becomes final and after each nightly refresh.
- **Settled scan:** every job is finished and every job that produced a report is imported. Failed, cancelled and timed-out jobs do not hold a scan back
  and are listed in `verdict_detail.incomplete_tools`; jobs whose output is only stored (Syft) are `stored_only_tools`. A scan with nothing to judge stays
  `pending`.
- **dojo-init:** waits for `GET /api/v2/` (any status below 500), logs in as `admin` (token kept in memory only), creates or verifies `securescan-sync`
  (staff) and `securescan-accounts` (superuser), stores each token as an encrypted `Credential` (kinds `defectdojo_token`, `defectdojo_admin_token`),
  enables deduplication and creates the two product types **with the superuser token** (spike M1 found `system_settings` superuser-only), records the
  admin's `last_login` as the break-glass baseline. Each service account's generated password is stored encrypted in `Credential.extra.password_enc`
  (context `credential-password:<id>`), which lets a revoked token be replaced; if the user exists but no credential does, dojo-init stops with an
  instruction instead of deleting the user (deleting a user that imported findings may cascade). Everything it changes is printed and logged.
- **Accounts:** at sign-in (`@on_login`, 5 s timeout, no retries) the hook creates the DefectDojo user (username = lower-cased UPN local part, `-<oid6>`
  suffix on a clash or a reserved name; Admin = superuser + staff, Analyst = staff; random 20-character password; `force_password_reset` through
  `user_contact_infos`), stores the password encrypted on `User.dd_initial_secret` and later syncs role flags. `GET /me/defectdojo-account` shows the
  password once (and clears it) and also provisions lazily when sign-in could not. Expiry: no sign-in for 90 days disables the DefectDojo account
  (`defectdojo_account.expire` audit event); the next sign-in re-enables it, an Admin disable is never undone automatically (the reason is read from the
  audit log, no new column). Activity is `max(created_at, last_login, updated_at)`, so an Admin enabling an account restarts its clock.

## Deviations from the plan or the design (with reason)

1. **DefectDojo runs on its own internal network `dojo`, not on `backend`.** An `include`d file is loaded as a separate model, so it cannot reference the
   parent's `backend` network or `db` service. `db`, `api`, `worker`, `gateway` and `dojo-init` join `dojo` in `compose.yaml`. The network is `internal`, so
   DefectDojo cannot reach the Internet.
2. **Nested include**: `compose.yaml` includes `compose.defectdojo.yaml`, which includes upstream + override with `project_directory: .` (paths resolve
   against `deploy/`).
3. **No `depends_on: db` on the initializer** (same reason). Instead every DefectDojo entrypoint is overridden to `wait-for-it.sh db:5432 -t 300` and the
   initializer has `restart: on-failure`. `depends_on: postgres` is dropped everywhere (`!override`), the upstream service stays defined under the profile
   `disabled`.
4. **Secrets are files, not environment values**: `DD_DATABASE_URL_FILE` reads the new secret `dd_database_url` (made by `dev.py secrets init` from
   `defectdojo_db_password`, TLS `verify-full` against our CA) instead of `DD_DATABASE_URL=...${DD_DB_PASSWORD}` (a password in `docker inspect`). The upstream
   variables are removed with `!reset null` because DefectDojo's secret loader may refuse a variable and its `_FILE` twin. `tls_ca` is mounted from a
   differently named secret (`dd_tls_ca`) to avoid a name clash with the parent file; the admin password is `dojo_init_admin_password` in the parent for
   the same reason.
5. **`deploy/defectdojo/upstream/docker-compose.yml` is a placeholder** written from the research notes and `spikes/s1/docker-compose.yml`; its header says
   to replace it with the verbatim 3.4.0 file on first run (command inside the header).
6. **`DD_HASHCODE_FIELDS_PER_SCANNER` is not set**: DefectDojo's defaults apply until spike S1 decides (the override has a comment showing where).
7. **Counts come from the findings read, not from `statistics.after`.** The response statistics are kept in `dd_import_stats`, and a mismatch is logged as
   `import_counts_differ`. Reason: history rows and counts must agree. The design's "take the response counts when complete" saved one request that is made
   anyway for history.
8. **dojo-init uses the superuser token for system settings and product types** (not the sync token), see M1 notes deviation 2.
9. **Password reset may not work**: spike S1 read 3.4.0 as refusing `password` in `PATCH /users/{id}/`. The endpoint returns a 503 problem saying an Admin
   must set it. Delete-and-recreate was rejected on purpose (a user's notes and findings may cascade). See "Not verified" for the fallback runbook line.
10. **`import_state` of a job with nothing to import is set to `imported`** with `dd_import_stats = {"skipped": reason}` (M3 uses `mark_import_skipped` the
    same way), so the scan is not held `pending`. The portal shows the derived words `skipped` / `not_applicable` (`import_status` in the results API).
11. **Extra periodic task `import_sweep`** (every minute) and a per-Test lock; the plan listed no sweeper but the outbox needs one for backoff and lost defers.
12. **`securescan/security/csv_safe.py` is created here**: M2's notes say M4 owns it, the M4 task text says M2 does; it did not exist.
13. **Policy API** adds `PATCH /policies/{id}` and `GET /policies/builtin`; a policy has exactly one scope (application, classification or default) and the
    thresholds shape `{"fail": {"critical": 1, "high": 6}, "conditional": {"high": 1}}`. Editing thresholds bumps `version`; scans record the version
    they were judged by in `verdict_detail.policy`.
14. **`GET /integrations/defectdojo` is readable by Analysts**, the outbox and account endpoints are Admin only.
15. **`GET /me/defectdojo-account` changes state** (it clears the stored initial password as it returns it, and may provision). The response is `no-store`.
16. A DefectDojo user adopted by name (created by hand) gets no initial password; the user sees `password_shown` only after a reset.

## Not verified, and how to verify on Ubuntu 24

Run first, from `backend/`: `uv run ruff format . && uv run ruff check . --fix && uv run mypy securescan && uv run pytest tests/unit` (the unit tests for this
milestone are the files listed above). Then, in this order:

1. **Replace the upstream file**: `curl -fsSL https://raw.githubusercontent.com/DefectDojo/django-DefectDojo/3.4.0/docker-compose.yml -o deploy/defectdojo/upstream/docker-compose.yml`,
   then `docker compose --project-directory deploy --env-file deploy/.env --env-file deploy/images.env -f deploy/compose.yaml config`. Check: services
   `nginx uwsgi celerybeat celeryworker initializer valkey dojo-init` are present and `postgres` is not started; no `ports` on `nginx`; every DefectDojo service
   has network `dojo` and the secrets; `DD_DATABASE_URL` is absent and `DD_DATABASE_URL_FILE` present; entrypoints use `db:5432 -t 300`; the bind mount of
   `extra_settings` points at `deploy/defectdojo/extra_settings`. The least certain Compose points are: nested `include`, `project_directory` for the nested
   include, `!reset null` on an `environment` key and on `depends_on`, `!override` on `entrypoint`, a YAML anchor holding a list used for `secrets:`, and
   an included file whose services the parent file references (`dojo-init` depends on `uwsgi`, the parent's `networks: [dojo]`). If `config` refuses one of them,
   the fallback is to list both files with `-f` in `scripts/dev.py` instead of the `include`; record it in `docs/decisions.md`.
2. **Entrypoint script names** in the override (`/entrypoint-uwsgi.sh`, `-celery-beat.sh`, `-celery-worker.sh`, `-initializer.sh`) and that DefectDojo's secret
   loader honours `DD_DATABASE_URL_FILE`, `DD_SECRET_KEY_FILE`, `DD_CREDENTIAL_AES_256_KEY_FILE`, `DD_ADMIN_PASSWORD_FILE`: `docker logs securescan-initializer-1`.
   Also `DD_SESSION_COOKIE_SECURE`, `DD_CSRF_COOKIE_SECURE`, `DD_CSRF_TRUSTED_ORIGINS`, `DD_OS_MESSAGE_ENABLED`, `DD_DEDUPLICATION_ASYNC_WAIT_TIMEOUT` exist in
   3.4.0's `settings.dist.py`. `docker exec securescan-db-1 psql -U postgres -d defectdojo -c '\dt'` must list tables.
3. **`python scripts/dev.py secrets init`** creates `dd_database_url`; if secrets already exist from M0, delete `deploy/secrets/dd_credential_aes_256_key`
   first (the old file has 64 characters) and run it again.
4. **dojo-init**: `docker logs securescan-dojo-init-1` shows the changes; a second `docker compose ... up -d dojo-init` prints `nothing to change`.
5. **Spike S1 facts** to confirm against the code (each is one line in `client.py` or `findings.py` if it differs): `?id=1,2,3` filter works (else the
   fallback is used automatically; look for the log line `defectdojo_id_filter_ignored`), findings carry `last_status_update`, `vulnerability_ids`,
   `cvssv3_score`, `component_name`, `hash_code`, and what a DAST finding offers for its URL (`finding_url`, DefectDojo 3.0 locations); `user_contact_infos`
   accepts `force_password_reset`; `PATCH /users/{id}/` with `password` (the reset path); `statistics.after.<severity>.active` shape (only a cross-check).
6. **Reimport**: the acceptance run of the plan (`js-planted` with Semgrep + Gitleaks): Organization `Internal Applications`, Asset `js-planted`, Engagement
   `main`, two Tests; the re-run adds and closes nothing; removing a planted issue closes exactly one finding and `state_now` changes after
   `docker exec securescan-worker-1 python -c "import asyncio; from securescan.jobs.history_sync import run_history_state_refresh as r; print(asyncio.run(r()))"`.
7. **Outbox**: `docker stop securescan-uwsgi-1`, run a scan, start it again; `GET /api/v1/integrations/defectdojo/outbox` shows attempts and the import
   succeeds within a minute or two of DefectDojo returning (the sweeper). Check the Procrastinate points: `@app.periodic` with `queueing_lock` (as M2),

## Open issues for other milestones

- **M3** (already wired): `enqueue_import`, `enqueue_report`, `finalize_scan_if_ready`, `mark_import_skipped` are called by `runner/executor.py`,
  `runner/recovery.py` and `domain/scans.py` with the signatures here. `enqueue_import` **commits the session it is given**. Cancelled jobs are settled through
  it (they are "not applicable"). `scan_job` must store the raw report as an `Artifact` of kind `raw_report` with `job_id` set and `filename` equal to the
  catalogue's `defectdojo_file` before calling it (the import looks the file up that way).

  verdict leaves `pending` (and again after a dead-letter replay). `scan_findings(include_inactive=False)` returns rows whose `state_now == "open"`;
  `include_inactive=True` returns every row of the scan (check `state_now` yourself). `refresh_scan_state` needs the sync token (credential), so a report can
  fail to refresh while DefectDojo is down; M5 already treats that as best effort.
